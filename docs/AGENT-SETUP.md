# Wiring lightspeed into a coding agent

`lightspeed mcp` serves a coding agent such as Claude Code the questions it asks about a
codebase — search symbols, read one symbol instead of a file, who uses this, what breaks
if I change it — as MCP tools. This page is how to set that up in Claude Code, what to
expect from the tools, and how to take it out again.

The set of agent-facing capabilities is checked by a test (`internal/cli/capabilities_test.go`):
every capability in it must map to a command that exists in the command table and is exposed
over MCP. The agent policy text is generated by `lightspeed guide` from the same command
table, so it cannot name a tool this build lacks.

## How the answers are produced

Lightspeed asks the **language server** (gopls, rust-analyzer, pyright, …) and keeps only a
cache that **revalidates against the disk on every query** (D32–D33).

- Answers are semantic (real references, real call graphs, real types) and never older than
  the file on disk. There is no index to build before asking, nothing to notify after an
  edit, and no hook to keep anything fresh.
- You need a language server installed for each language you want symbol answers for
  (`lightspeed doctor`, `lightspeed install <name>`), and a server that is still indexing
  answers **exit 5 / `not_ready`**, never an empty list. Treat 5 as "wait and retry".
- A language with no server still gets `search_text`, `tree`, `file` and, for the
  languages that have an import extractor (Go, Python, TypeScript/JavaScript, Rust, C/C++,
  Lua), `imports`, `find_importers` and the dependency graph.

## The tools

`lightspeed X` is the CLI command; over MCP the tool has the same name unless noted and, in
Claude Code, appears as `mcp__lightspeed__<tool>`. `lightspeed guide` is the full policy
(which tool for which question, how to name a symbol, what the exit codes mean); this is the
short form.

| question | command | notes |
|---|---|---|
| Is the workspace ready, what is covered? | `index status` (MCP `index_status`) | There is nothing to resolve: the workspace is the git/project root of the working directory. Reports counts, coverage per server and language, files skipped and why, staleness and the cache path. It builds nothing. |
| Warm the index | `index build` (MCP `index_build`) | Optional. Every query builds what it needs, lazily, and revalidates the rest; `index build` only warms it. `index clear` forgets the cache; it is a cache only. |
| Where do I start on this task? | `task_context` | No model: it extracts identifiers from the task text, ranks symbols, expands the best few by callers, callees and imports, and returns a `--budget`-bounded capsule with a confidence (high, medium, low), the reason, and the rule in a line (`--rule` for the full text). Low confidence says "probably not implemented here" instead of padding with weak matches. |
| A symbol by name | `search_symbols` | Exact name, then prefix, then BM25 over name, container, signature and doc sentence (camelCase and snake_case split); every row says how it matched and its score. Fuzzy is opt-in (`--fuzzy`) and only when nothing else matched. Kinds are the language server's. `--limit` defaults to 20 and truncation is reported with the total. |
| A string, comment or config value | `search_text` | A live scan of the working tree (gitignore-aware): substring or RE2 regex (`--regex`), `--word`, `--glob`, `--path`, `--limit`. `--with-symbol` adds the id of the symbol containing each match when a server can say. |
| What is in this file? | `outline` | Takes several files. Each symbol has an id `path::Container.Name#kind[~N]`; the kind is the server's SymbolKind name and `~N` numbers duplicates in a file. Ids are recomputed on every use and never stored: a stale one is a `stale_id` error naming the nearest candidates. Take ids from lightspeed's own output rather than building them. |
| One symbol's text | `source` | Byte-exact text with the doc comment and a content hash, `--max-lines`/`--max-bytes` caps that report `truncated`. Accepts ids and locations (`file:line`). The text is read from the disk at the moment of the call. |
| One symbol with its surroundings | `context` | One symbol, its file's package/import block and the server's hover text. Call it per symbol. |
| A file that has no symbols | `file` | Reads the working tree, confined to the workspace (`..`, absolute paths and symlinks that leave it are `outside_workspace`). Use `outline` and `source` for code. |
| The shape of the repository | `repo_outline` | Directories with file counts, language breakdown, the servers that handle them and whether they are installed; per-directory symbol counts appear once the index is warm. |
| The file list | `tree` | Gitignore-aware; each file carries its language and the server that handles it. `--prefix` and `--max-files` (default 500, truncation reported). |
| The important files | `repo_map` | Files ranked by PageRank over the import graph with their top symbols, within `--budget` tokens (default 2000); what was left out is reported. Needs an import extractor for the language. |
| Who imports this file or package? | `find_importers` | Takes a file, a package directory or a Go import path. A language with no extractor is `not_covered` (exit 3), never an empty list. `--limit` bounds the list and test-only importers that were left out are noted. |
| Who references this symbol? | `references` | The language server's semantic references at a position, id or `--symbol`. |
| Is this name used anywhere at all? | `check_references` | Semantic references when the name resolves to a symbol, plus `search_text` hits for the bare identifier outside those (strings, comments, configs, other languages), in a separate section. A bare name that matches several symbols gets the verdict `ambiguous`, with a reference count per candidate. |
| The import graph | `dependency_graph` | Edges from a file, directory or Go package (`--depth`, `--direction out|in|both`, `--external`), or the whole workspace. |
| Import cycles | `dependency_cycles` | Strongly connected components of the import graph; exit 1 when there are any. |
| What breaks if I change this? | `blast_radius` | For a symbol or a file: a summary first (counts, distinct files and packages), then rows, each saying which evidence it comes from: direct references grouped by file and enclosing symbol, transitive callers to `--depth`, importing files to `--import-depth`, and which of those are tests. Bounded by `--limit`; a cut is reported. |
| Which symbols did this diff touch? | `changed_symbols` | Maps the hunks of `git diff` (`--base <rev>`, `--staged`) onto symbol ranges: added, modified and removed symbols by id. Outside a git repository it degrades with a warning. |
| What is unused? | `dead_code` | Candidates, not verdicts: symbols with no references outside their own declaration, excluding entry points (main, init, tests, interface implementations, exported API unless `--include-exported`, the `[dead_code]` table of `.lightspeed.toml`). Bounded and resumable (`--kind`, `--path`, `--limit`, `--budget`, `--cursor`) and reports how much it examined. Each candidate has a confidence. |
| Supertypes and subtypes | `type_hierarchy` | The server's `typeHierarchy` (`--direction`, `--depth`). A server without it falls back to `implementation` for subtypes, and the answer says so. |
| Callers and callees | `call_hierarchy` | Incoming and outgoing calls with `--direction` and `--depth`, bounded, cycles reported once. |
| Who implements this? | `implementation` | The server's `textDocument/implementation` at a location, id or `--symbol`. |
| What goes with this symbol? | `related` | Small and ranked: same-file siblings, callers and callees at depth 1, files that change together in git history, and similarly named symbols from the index. |
| Can I rename this? | `rename_check` | A read-only verdict with evidence: the server's `prepareRename`, a preview summary (files and edits, nothing written) and collisions with existing names found through the index. To do the rename: `rename … --apply`. |
| Can I delete this? | `delete_check` | A read-only verdict with evidence: references outside the declaration and, when it is the last symbol of a file or package, the importers that would break. |
| What changes often? | `churn`, `hotspots` | Commits, authors and lines per file (and per symbol where ranges allow) for `--since`; `hotspots` ranks churn times size. Both shell out to git. `hotspots` ranks code only unless `--all`. |

Everything a lightspeed tool returns is one JSON envelope, `{"ok":true,"data":…,"warnings":[…]}`
or `{"ok":false,"error":{"code","message"}}` (a tool error over MCP). Lists are bounded and say
`truncated:true` with the total when they are cut; `--limit` (`limit` over MCP) raises or lowers
the bound. Paths are workspace-relative in and out.

Exit codes matter to a script and, through `warnings`/`error.code`, to an agent: 0 ok · 1 problems
found, including an authoritative empty answer · 2 usage · 3 no server for the language, or
`not_covered` · 4 crash or timeout · 5 the server is still indexing (`not_ready`).

## What lightspeed does not do

- **Embeddings and meaning-based search.** There is no model and no vector store.
  `task_context` and `search_symbols` rank by names, signatures and doc comments; `--fuzzy`
  catches typos.
- **Generated summaries.** Symbols carry the server's signature and the first sentence of
  their doc comment; nothing is written by a model.
- **Runtime traces and coverage.** Lightspeed never runs your code.
- **Session state.** The tool list is the same for every model, and no state is kept
  between calls; an agent's own context already holds what it read.
- **Cross-repository queries.** One workspace per daemon; nothing is indexed across
  repositories.
- **Languages without an installed server.** Only `search_text`, `tree`, `file` and (for the
  languages with an import extractor) the import-graph commands work there. `lightspeed doctor`
  names what is missing; installing a server per language is the real cost of this design (D37).

## Why no hooks are needed

Some agent integrations install hooks to re-index a file after an edit or to nudge the agent
toward their tools. Lightspeed has no prebuilt index to keep in step: every query revalidates
the files it reports on against the disk (a stat, then a hash where the stat moved), and the
daemon tells its language servers about files changed outside lightspeed before it answers.
An edit made by Claude Code, an editor or `git checkout` is therefore seen by the next call
with nothing to notify. The nudge is in the MCP server's instructions and in the CLAUDE.md
section that `lightspeed guide --format claude-md` generates.

## Setup for Claude Code

Nothing below is done for you; every step edits your own files. **Back up the file you will
edit first**:

```sh
cp ~/.claude/CLAUDE.md ~/.claude/CLAUDE.md.pre-lightspeed
```

1. **Install lightspeed.** From a checkout: `make install` (or `go install ./cmd/lightspeed`); make sure
   `lightspeed` is on the `PATH` Claude Code starts with. `lightspeed version` prints the build.
2. **Install language servers.** `lightspeed doctor` diagnoses the setup for the current directory
   (config layers, executables, mise, routing); `lightspeed servers` lists what is configured and installed.
   For each missing server, `lightspeed install <name>` prints the exact `mise` command; run it, or run
   `lightspeed install <name> --run` (refused with `--offline`). Nothing is downloaded implicitly.
3. **Add the MCP server.**

   ```sh
   claude mcp add --scope user lightspeed -- lightspeed mcp
   ```

   (`--scope project` or `--scope local` to limit it; `claude mcp list` shows what is registered.)
   Restart Claude Code so it reads the new tool list. If you want an allow rule under
   `"permissions"` in `~/.claude/settings.json`, it is `"mcp__lightspeed__*"`;
   `python3 -m json.tool ~/.claude/settings.json > /dev/null` checks that the file is still valid
   JSON after editing it. No hooks are needed (see above), so nothing else in `settings.json` changes.
4. **Add the policy to `~/.claude/CLAUDE.md`.** Paste the output of

   ```sh
   lightspeed guide --format claude-md
   ```

   The section is framed by `<!-- lightspeed guide v1 build … -->` and `<!-- /lightspeed guide -->`, so it can
   be regenerated after an upgrade: replace what is between (and including) the two markers. This does it:

   ```sh
   python3 - <<'PY'
   import pathlib, re, subprocess
   p = pathlib.Path.home() / ".claude" / "CLAUDE.md"
   new = subprocess.check_output(["lightspeed", "guide", "--format", "claude-md"], text=True)
   old = p.read_text()
   pat = re.compile(r"<!-- lightspeed guide.*?<!-- /lightspeed guide -->\n?", re.S)
   p.write_text(pat.sub(lambda m: new, old) if pat.search(old) else old.rstrip() + "\n\n" + new)
   PY
   ```

   If CLAUDE.md already carries a code-navigation policy for another tool, delete that
   section rather than keeping two that disagree.
5. **Verify.** In a project: `lightspeed servers` (each server for the project's languages is installed),
   `lightspeed search_symbols <a name you know> --limit 3`, then start Claude Code and ask it to find that
   symbol; it should call `mcp__lightspeed__search_symbols`. The first query in a workspace builds the
   index (the warnings say how long); a language server that is still indexing answers `not_ready` (exit 5) —
   wait and retry, it is not "no results". `lightspeed daemon status` shows the warm servers.

## Rollback

1. `claude mcp remove lightspeed` (with the same `--scope` you added it under).
2. Restore the backup: `cp ~/.claude/CLAUDE.md.pre-lightspeed ~/.claude/CLAUDE.md`, or delete the
   section between the two `lightspeed guide` markers. If you edited the file after the setup,
   merge instead of overwriting.
3. Restart Claude Code.
4. Optional: `lightspeed daemon stop` in the workspaces you used, and delete the cache under
   `$XDG_CACHE_HOME/lightspeed/` (it is only a cache).
